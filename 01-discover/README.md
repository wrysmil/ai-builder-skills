# 🔍 01-discover — 发现真问题，在写第一行代码之前

> **要回答的问题：谁在疼？疼到什么程度？他会为此付钱还是只会说"这想法不错"？**

## 什么时候进入

- 当有人跟你说"这个需求很痛"，但你说不出他具体在哪里、什么场景下疼的时候。
- 当你准备开工，却拿不出任何一条付费或替代方案层面的证据的时候。
- 当你的想法还只是一句话，连目标用户是谁都没定下来的时候。
- 当别人给你的只是一个模糊抱怨，需要判断它属于提案、Issue 还是缺陷报告的时候。
- 当你已经动手做了一部分，但心里始终不确定需求是不是真的的时候。

## 什么时候不该进入

- 需求已经有明确证据（真人真金白银、明确的工作流阻塞），你要做的是把它写成计划 —— 直接去 `02-design`，不要在这里补仪式感的访谈。
- 你只是想把已有的 bug 报出来 —— 那是缺陷报告，用 `project-planner` 归类即可，不需要重新验证需求。

## 产出物

- 一份带编号台账的《开工前需求分析》：证据（E）、痛点（P）、业务能力（C）、一期需求（R）互相追溯，附验收指标与开工建议（可开工 / 先试点 / 先验证 / 暂缓）。报告骨架见 [`analyze-prebuild-needs/references/kickoff-report.md`](analyze-prebuild-needs/references/kickoff-report.md)。只要底座选型时，交付候选对比和逐项覆盖证据，格式见同一模板的「仅找底座时的紧凑输出格式」。
- 一份写满 20 条以上原始访谈原话的 md 文件，原话可追溯，不是你的转述和概括。
- 一份能被证伪的需求假设：写成"如果……那么……"的形式，并且明确什么结果会推翻它。
- 明确的用户画像：谁、在什么场景、多久遇到一次、现在用什么办法凑合。
- 一份能被证伪的需求假设整理后的提案 / Issue，可直接交接给下一阶段。

## 技能

| 技能 | 什么时候用它 |
| --- | --- |
| [`analyze-prebuild-needs`](analyze-prebuild-needs/) | 新系统、内部工具或平台立项，要验证业务问题与一期范围，或要根据需求主动找开源底座、核验指定平台时 |
| [`pain-point-discovery`](pain-point-discovery/) | 有人说"这个需求很痛"、你准备开工但拿不出付费证据时 |
| [`brainstorming`](brainstorming/) | 想法还很模糊、需要发散和澄清时 —— **任何创造性工作的硬性前置门槛** |
| [`project-planner`](project-planner/) | 想法已经清楚，要转成提案 / Issue / 缺陷报告时 |

## 常见反模式

**「我朋友都说好」** → 朋友的社交成本是零，他夸你的想法不需要付出任何代价，所以这句话不含任何信息量。

**「我 8 成同事都愿意用」** → "愿意用"和"愿意付费"之间隔着一整个商业模式，同事还是你的社交圈。

**「这个需求显而易见，不需要验证」** → 越是显而易见的痛，越可能已经有人解决了，你甚至没去看过现有替代方案。

**「先做出来再说，用户会自己来」** → 这是把验证成本推给了未来的自己，死掉的项目大多死在这一句话上。

## 下一步

拿到至少一条可证伪的需求假设和明确的目标用户画像后，进入 `02-design`。如果访谈反复得不到付费意愿、或者发现目标用户根本没有这个场景，就应该推翻假设回到起点重选问题，而不是硬着头皮往下做。

# 开工前需求分析与底座评估

从目标角色要完成的任务和可观察结果出发，形成可追溯的一期范围、复用判断和开工建议。业务证据说明需求为什么成立，技术证据说明具体版本和交付方式能做到什么。两类证据各自核验。

## 不适用

- 单个缺陷归档和修复 → `project-planner`
- 痛点真假判断和付费意愿验证 → `pain-point-discovery`
- 已有明确功能提议的投入产出评审 → `evaluate-feature-value`
- 功能列表裁剪和 MVP 范围 → `mvp-scoping`
- 纯实现和架构设计 → 对应技术流程

## 1. 确定当前要做的决定

- 收集需求原文、访谈、工单、样表、流程记录、日志和已有系统资料。给每条可定位的原始材料编 E 号，记录来源位置、日期或版本、可支持的结论和局限。标出已观察事实、当事人反馈、明确决定、分析推断和待核实事项。材料互相冲突时，记录适用人群、时间和范围，指出哪项核验能解决分歧。
- 用角色、触发条件、任务、期望结果、现有做法描述业务。记下影响选型的硬约束和偏好，分别标注来源和确认状态。能先做的分析先做，只在缺失信息会改变一期范围或候选筛选时集中追问。缺数据就写待测或待定，给出取数办法。
- 完整立项执行全部阶段。用户明确要先找底座时，先从现有描述提取临时需求和约束，然后直接检索，标注哪些条件会改变候选排序。用户限定只核验指定项目时，进入版本化核验，按指定范围交付。

## 2. 还原真实流程与痛点

- 优先追踪近期实际发生的一笔业务，从触发到完成，记录参与角色、操作、交接、异常、补救方式和实际结果。用访谈还原行为，用工单、日志、样表等回查能查到的细节。只有构想或竞品链接时，写出待验证的工作流和假设，保留可用的初步分析。
- 给痛点编 P 号并关联 E。写清谁在哪一步被卡住、现在怎么补救、发生频次、后果和测量口径。区分症状与原因，记录可推翻原因假设的证据。考虑是否存在更小的流程调整、已有工具配置或现成服务可解决问题。
- 缺少决定性业务事实时，安排最小取证动作，写清找哪个角色、检查哪段记录、观察什么结果会支持或推翻假设。公开市场、竞品和开源项目可以帮助识别品类、术语和实现路径。用目标组织自己的记录、行为或明确约束确认本项目的需求。

## 3. 把需求变成可以逐项核验的用例

- 按流程拆业务能力 C。根据核心任务识别主品类，只有相邻品类会影响范围或搜索时才纳入。把角色动作、数据变化和关键异常转换成逐条可执行的一期需求 R。每条 R 关联 P、C 和 E，或直接追溯已确认约束。按影响、频次、证据强度、依赖和成本取舍，保留低频高后果事项。
- 为 R 写角色、前置条件、动作、期望结果和验收口径。权限、异常、存量迁移和审计等相关条件写进用例。标注必需／可选、一期／后续、确认状态和业务验收状态。把功能点、业务规则和实现设想分开，避免候选项目反过来定义原需求。
- 搜索前记录本轮使用的 R 清单、必需项、硬约束、已知假设。已知约束可据此筛除候选。会改变结论的假设要带进结果。业务方调整范围时，说明依据并用同一更新口径复核相关候选。

## 4. 主动发现底座并逐项尽调

用户要求找底座，或复用会影响范围、成本与开工决定时，实际执行检索，即使没有产品名。按业务结果判断有哪些适用路径，包括现有系统配置或流程调整、开源平台、可组合组件，以及自建。对需要外部检索或候选尽调的任务，按 [开源底座检索与核验手册](references/foundation-research.md) 执行工具选择、查询、证据升级和并行策略。

1. **搜候选。** 从主品类、关键业务动词、同义词、部署或集成约束生成不同检索式。用仓库检索和通用 Web 搜索发现候选，再打开官方仓库、官网和一手材料核验。AI 提名、目录和搜索摘要只提供线索。仓库不可访问时记录状态及尝试过的渠道。无可用检索工具时交付检索式、待查来源和当前影响。
2. **筛硬约束。** 对每个真实候选记录产品、仓库、目标版本或提交、版本类型、部署模式和观察时间。先筛许可证、部署、数据、关键集成及其他已确认硬约束，按满足／不满足／待核实登记。已知硬约束冲突的候选给出淘汰原因。关键硬约束未知的候选只可待核实或有条件试点。
3. **逐 R 核验。** 对进入详评的候选用同一 R 清单，把具备／部分具备／不具备／待核实逐格关联至版本化文档、源码与测试，或实际运行记录。记录默认支持、配置、插件、二开等交付方式，写明缺失环节、适配与维护成本。必要时对会改变决定的用例设计验证，并说明试验环境、通过和停止条件。候选能力核验不会自动改变生产验收状态。
4. **综合比较。** 先比较硬约束和必需用例，再考虑适配、迁移、运维、升级和退出成本。默认呈现必需项和全部评价项的状态分布，附证据和排序理由。用户需要百分比时，公开分母、权重和算法，另外单列未知与阻断项。把候选缺口回写到对应 R、验收用例、实现路径和开工条件。

## 5. 判断开工并交付

先给适用范围和建议，再按 [报告模板](references/kickoff-report.md) 交付相应章节，保留影响结论的证据、缺口和取舍。默认在对话交付，用户要求落盘时沿用项目文档位置与格式。

- **可开工**。核心流程有业务依据。一期必需项有可执行验收标准，硬约束和关键依赖已有证据支持的可行路径。附可开工的工作包及前提。
- **先试点**。问题有依据，关键适配疑问可由小范围、可逆的试验解决。说明试点范围、适用约束、数据、通过和停止条件，以及结果如何影响选型。试点证据限定在实际覆盖的环境和用例内。
- **先验证**。关键痛点、前提或阻断项缺乏证据，现有材料不足以支持开工。给优先级最高的取证动作和下一次决策条件。
- **暂缓**。证据显示收益有限或拟采用路径与已确认硬约束冲突，且当前没有可行解法。说明恢复条件。某候选被淘汰时，继续比较仍可行的路径。

交付前检查每条必需 R 能追溯到材料或约束，候选结论指向同一版本和类型，排序如实体现未知和阻断，关键缺口有验证动作，数值与项目状态有可定位的依据。

## Red Flags

- 把 AI 提名或搜索摘要当作已验证候选，跳过仓库核验
- 见功能名就标「具备」，不查版本化源码或文档
- 跨版本拼凑能力：用 main 分支文档证明旧版本的能力
- 高覆盖率掩盖硬约束冲突（如许可证 AGPL 与部署要求冲突）
- 用候选的功能列表反推原需求，导致需求被候选塑造
- 只搜一个渠道、一组关键词就锁定候选

**出现任一条：回到对应步骤补证据。**

## 常见错误

| 错误 | 修正 |
| --- | --- |
| 材料只有口述，不标来源和日期 | 每条 E 记位置、日期、可支持的结论和局限 |
| 把意愿当行为证据 | 区分已观察事实和当事人反馈，标注类型 |
| 比较不同版本或部署模式下的能力 | 锁定同一版本和部署模式再逐 R 核验 |
| 一个候选淘汰就停止搜索 | 保留搜索边界和淘汰原因，继续比较可行路径 |
| 试点结论推广到全量 | 标明试点覆盖的环境和用例范围 |
| 只用 README 功能名判断覆盖 | 验收条件超出描述时，补查源码、接口或测试 |

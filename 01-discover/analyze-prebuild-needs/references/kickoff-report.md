# 开工前需求分析报告模板

从当前决定、适用范围和建议开始。完整立项使用下列各节。只找底座或核验指定项目时，保留已知业务边界、临时需求、约束、候选证据和下一步，说明哪些信息会改变结果。

## 1. 开工建议与业务边界

| 内容 | 记录字段 |
| --- | --- |
| 建议 | 可开工／先试点／先验证／暂缓，适用范围，主要依据，开工前提，下一次决定 |
| 业务边界 | 目标角色、触发条件、要完成的任务和结果、主品类、相关流程、现有做法、本轮明确排除的范围 |
| 影响选型的条件 | 硬约束或偏好、适用范围、来源 E、确认状态、变更对范围或选型的影响 |

## 2. 从材料追溯到一期验收

| 台账 | 记录字段 |
| --- | --- |
| 资料 E | 编号，原始材料位置，日期或版本，涉及对象与范围，原始观察或原文摘录，能支持的判断和局限 |
| 痛点 P | 编号，关联 E，角色与流程步骤，卡点和现有补救，影响、频次和测法，原因假设，优先理由 |
| 业务能力 C | 编号，业务动作与结果，关联流程与痛点，依赖关系 |
| 需求 R | 编号，关联 P、C、E 或具体约束，角色、前置条件、动作、预期结果，权限或异常等适用条件，必需／可选，一期／后续，确认状态 |
| 验收 | 关联 R，用例、输入和期望结果，指标定义、当前基线、目标和测量方式，业务验收状态，结果证据 |

基线和目标未确定时写待测或待定，并注明获取方式。需求确认状态记录业务方确认和证据情况，业务验收状态记录实际验收结果。候选项目文档或隔离试验的结果记入候选覆盖矩阵。

## 3. 候选发现、筛选与逐项核验

| 记录 | 字段 |
| --- | --- |
| 检索记录 | 日期、范围、需求清单版本、渠道、实际查询、命中、未能核验的提名和覆盖边界 |
| 候选与硬约束 | 规范仓库或源码发布入口、目标版本或提交、版本类型、部署模式、核验日期、逐条硬约束结果和证据、处置理由 |
| 逐项覆盖 | 候选与对应 R／用例，具备／部分具备／不具备／待核实，证据出处与支持范围，可用方式，已知缺口与未知，下一验证动作 |
| 路径比较 | 已确认冲突、关键未知、必需项与全部评价项状态分布，改造、迁移、运维、升级及退出工作，首选和有条件备选，调整建议的条件 |

同一需求在各候选上沿用相同的验收口径。若报告采用覆盖百分比，同时注明分母、权重、算法、未知和阻断项。保留被淘汰候选的理由和证据。

### 仅找底座时的紧凑输出格式

用户只点「先找开源基础软件」或只给了简短需求描述时，省略完整立项台账，按以下结构交付。

**检索透明度**（放在候选列表前）：

- 考虑的底座品类和提炼的关键能力
- 实际使用的搜索词和渠道
- 忽略的 AI 提名（不存在、不可读取或已归档的项目，附尝试过的 URL 或原因）

**单候选卡片**（每个候选一张，按匹配度排序）：

```
## <项目名> ↗                        命中来源 · 匹配 N%

据 README，<一句话说明适合做什么底座和已确认能力>；<关键未确认项>。

入选理由：<用什么检索词/渠道命中，为什么方向契合需求>
★ <星标> · <语言> · <最近更新> · <许可证标签，传染性许可高亮提醒>

具备 N · 部分 N · 不具备 N · 看不出 N

二开风险：<逐条列出许可传染性、外部依赖、数据口径、
         迁移成本等具体风险，不用泛泛概括>

[查看逐项对照]  [选为基础软件]
```

- 匹配百分比 = 已证实具备的 R 权重之和 ÷ 全部评价 R 权重之和（等权时每项 1）
- 许可证标签对传染性许可（AGPL、GPL、SSPL 等）显式标红并说明二开后分发或网络服务场景的影响
- 「查看逐项对照」展开后，每条 R 对应具备／部分／不具备／看不出，附原文依据（README 段落、源码路径或「未找到相关描述」）
- 多个候选时，末尾附一段路径比较摘要，列出各候选的硬约束冲突、必需项覆盖差异和主要取舍

## 4. 缺口与验证计划

| 缺口及关联项 | 已证实内容与未知 | 取证或试验动作 | 判定标准与决策影响 |
| --- | --- | --- | --- |
| 关联 E／P／R、硬约束或目标候选 | 写明证据范围及为什么可能改变决定 | 写明对象、来源、执行方式、目标环境、样本或数据 | 写明预期结果、失败或停止条件，分别会改变哪些需求、候选路径或开工前提 |

先列影响最大的阻断项和能最快改变决策的验证。每项给出执行顺序，已有负责人或时间安排时一并记录。

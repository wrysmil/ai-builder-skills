# 开工前需求分析报告模板

## 阶段交付与确认记录

每轮只展示当前阶段的结果、证据局限和需要用户明确决定的事项。用「阶段｜结果版本｜状态｜待确认事项或用户决定｜下一步」记录。状态使用待确认、已确认、待复核。需要修订就更新当前版本，确认后才开始下一步。

| 阶段 | 阶段交付 | 用户确认点 |
| --- | --- | --- |
| 1. 判断品类 | 主品类及依据、参考品类及用途、候选池及来源、可取得的页面或运行证据 | 品类、业务边界、纳入后续研究的候选范围 |
| 2. 拆解能力 | 业务流程、E/P 证据与痛点、C/R 能力与验收用例、必需项和计分项 | 一期范围、必需项及对照口径 |
| 3. 对照底座 | 候选匹配度和四态计数、逐项证据、必需项缺口、二开成本和实施路线 | 拟采用的路径以及保留的缺口和前提 |
| 4. 沉淀方案 | 业务方案、验收、验证计划、开工条件及双格式报告 | 方案范围、验收与开工条件 |

只找底座时可以交付第 1 步候选池。只核验指定项目时按实际用例与确认状态交付相应部分，注明范围和证据局限。

## 第 4 步整合报告

复制下列七节骨架，用已确认的阶段结果和实际证据填充。报告标题使用《开工前需求分析——项目名》。报告开头记录日期、状态、阶段确认、评估版本、范围假设和证据层级。第 4 步待确认稿与定稿均可用同一结构。

| 章节 | 最少交付内容 |
| --- | --- |
| 1. 🧭 开工建议 | 可开工／先试点／先验证／暂缓，适用假设、主要依据、前提和下一次决定 |
| 2. 业务边界与现状 | 角色、触发条件、任务、现有流程、期望结果、主品类、相邻品类、影响选型的硬约束与偏好 |
| 3. 证据与痛点 | E 台账记录来源、日期、类型和局限。P 台账关联 E，记录卡点、补救、频次、影响和待验证原因 |
| 4. 一期范围与验收 | C 能力、R 需求、关联 P/C/E、必需或可选、确认状态、验收用例、指标基线和验收状态 |
| 5. 🔎 底座匹配与路径比较 | 5.1 检索记录与评分口径，5.2 候选逐项对照，5.3 需求覆盖矩阵与证据，5.4 路径取舍与缺口，5.5 实施路径对照 |
| 6. 🧪 验证计划 | 关联缺口、验证对象、样本、方法、通过或停止条件、结果怎样改变决定 |
| 7. 开工条件与待决事项 | 开工前提、仍待确认的选择、可先做的事项和后续范围 |

第 4 节为 R 写明角色、前置条件、动作、预期结果及适用的异常或权限。基线和目标缺数据时写待测或待定，附测量方式。候选的文档或试验结果放进覆盖矩阵，业务验收状态按实际验收记录填写。

## 5.2 候选逐项对照的必填表头

表前给出本轮考虑的底座品类、候选数量和对照的关键能力。关键能力沿用计分清单的编号或短名称，展开定义和验收条件放在第 5.1 节，逐项证据放在第 5.3 节。

| 候选及仓库 | 匹配度 | 四态计数 | 目标版本 | 许可 / 部署 | 依据 | 关键缺口与处置 |
| --- | --- | --- | --- | --- | --- | --- |
| 项目名与可点击的规范源码链接 | 例如 **88%（7/8）** | 具备 7 · 部分具备 1 · 不具备 0 · 待核实 0 | tag / commit，未锁定则标明证据范围 | 许可、模式、硬约束状态 | 官方版本化文档、源码或实测位置 | 入选用途、必需项覆盖、阻断、二开成本与处置 |

只在检索记录里保留来源无法核验的提名。商业工具和自有系统可作为对照，给出可追溯的官方入口或内部证据，并标明类型。候选对照按四舍五入前的已证实匹配度降序排列，同分时依次比较部分具备项数（多者在前）、待核实项数（少者在前）。仍同分可保持检索记录顺序。推荐资格由硬约束和必需项决定，实施取舍另看适配成本。组件注明用途，避免把低全局覆盖率解读成组件本身表现差。第 1 步候选池按[初步匹配度与推荐理由](foundation-research.md#初步匹配度与推荐理由)交付，包含排名、初步匹配度、品类、规范入口、分点理由、初筛限制和可取得的页面或运行证据。默认详列前 10 名，其余列附表。正式匹配表在第 3 步生成，矩阵范围与已确认的用例一致。

## 评分与证据口径

1. 以第 2 步用户确认的 R 清单或可独立核验的 R 子用例为准。列出各项定义、必需项、排除项、允许的交付方式。所有候选使用同一分母。子用例评分仅代表该子用例覆盖。
2. **已证实匹配度 = 完全具备项权重之和 ÷ 全部评价项权重之和 × 100%**。默认等权，整数百分比四舍五入。仅采用业务方确认的非等权，同时给出权重。部分具备、不具备、待核实均不进入分子，四态分布保留它们的区别。分母为 0 时写「待评估（0 项）」并说明原因。
3. 在第 5.3 节逐项注明 ✓ 具备、◐ 部分具备、— 不具备、? 待核实以及证据、可用方式和不足。仅在有证据支持时判为不具备。待核实超过半数时，分数标「暂定」，另给出假设所有待核实项均具备时的上限。未锁定版本的分数标注证据版本或说明暂定。
4. 写明是否存在硬约束冲突、关键未知和必需项缺口，据此给出处置。区分文档核验、样片验证和业务验收。

## Markdown 与 HTML 双交付

- 两个文件使用同一文件名主干。Markdown 保留完整内容，HTML 使用相同内容和章节。正式报告使用普通 Markdown 标题、表格与链接，直接用少量 Unicode 图标给建议、覆盖状态、验证计划提供视觉提示。图标配文字。
- 用资产目录中的 `kickoff-report.html` 渲染成单文件 HTML。可从任意工作目录执行下列命令，将 `<技能目录>` 和文件路径替换为实际路径。Pandoc 处理 Markdown 表格、目录与锚点，模板内置样式。无 Pandoc 时使用可用的 Markdown 渲染器生成相同结构，并复用模板的样式和布局。正文不得依赖网络脚本、样式或字体。

```sh
pandoc --from=gfm-raw_html --to=html5 --standalone --section-divs --toc --toc-depth=2 --template="<技能目录>/assets/kickoff-report.html" --metadata pagetitle="开工前需求分析——项目名" "<报告>.md" --output="<报告>.html"
```

交付前检查候选数与表格行数一致，关键能力清单与矩阵列一一对应。复算每行四态计数、分子、分母和排序，检查两种文件的章节、表格和结论一致。确认 HTML 以 UTF-8 打开，目录可跳转，宽表在窄屏能横向滚动。

# 产品开工与原型评审

从用户要完成的任务出发，依次判断品类、拆解能力、对照底座、沉淀方案。业务证据用来确认需求，技术证据用来判断候选能覆盖什么。

## 按用户目标选择入口

**默认走完整立项，不允许无声降级。** 「帮我做个需求」「用这个 skill 做一下需求」「给我立项」「这个产品要做」「你看着办」这些都算完整立项。用户给的是背景 + 痛点 + 期望结果、没有现成 PRD 时，一律从第 1 阶段开始。需求描述短、口语化、像一句话，都不构成跳过阶段 1 底座检索的理由。

只有能指到用户原话或已存在文件时，才走捷径入口：

- **完整立项**：按下文四阶段推进。用户已经确认的决定直接继承。
- **直接写 PRD**：用户明确要求直接写、修订或续编 PRD 时，按 [七节 PRD 骨架](references/kickoff-report.md) 与 [填写规则](references/prd-structure.md) 交付。底座一节按实际记录已评估、未评估或明确排除。用户排除底座评估时保留其决定，后续交付范围沿用用户要求。
- **只做 UI 或原型**：用户明确要求制作原型时，优先沿用已有 PRD。只有原始需求时，先从输入提取任务、页面和关键状态。按 [交互原型评审规范](references/prototype-review.md) 产出。
- **只找底座 / 只核验指定项目**：按给定范围交付，注明输入与证据局限。

判断不了就按完整立项起步，并在第 1 阶段开头用一句话说明：「我按完整立项推进，先判断品类和找候选底座；如果你只要 PRD 或原型，说一声我直接跳过去。」

## PRD 审查与交付时序

1. 阶段 1–3 按各自的确认点推进。阶段 4 和「直接写 PRD」都先整理七节内部稿。
2. **每次向用户交付 PRD 前，包括首稿、修订稿和定稿，必须完成[独立 PRD 审查](references/prd-review.md)。** 主 Agent 把原始材料、确认记录和内部稿交给子 Agent 查漏并拟写补充，等返回后逐条核对、补写并运行 PRD 校验。同一正文仅调整格式或状态时，让子 Agent 对照上次审查版本核对实际变更。若无法派遣或拿到有效审查，说明当前阻塞，保留内部稿并暂停 PRD 交付及下游原型。
3. **先单独向用户交付已审查的 Markdown PRD。** 说明补入了哪些需求和验收、仍有哪几项需要业务决定。收到用户确认或明确要求基于该版 PRD 制作原型后，才开始制作并另行交付交互原型。用户只要求 PRD 时到文档交付为止；只做原型时沿用已有输入和该入口的范围。
4. 「先验证」「先试点」可以写在 PRD 的开工建议中，附执行人、输入、阈值与产出证据。涉及界面时，开发和排期在原型评审后讨论；无界面的项目在 PRD 记录评审材料及确认条件。技术验证须按用户授权开展。

## 分阶段协作

- 新项目从第 1 步开始。每轮只推进当前阶段，先完成该阶段内可执行的工作，再交付阶段结果和需要用户确认的具体决定。后续阶段等当前结果经用户明确确认后启动，第 4 步也需用户确认才算定稿。
- 用户明确接受当前结果或要求基于当前结果进入指定下一步时，记录该决定并继续。静默、跳过问题、单纯补充资料或要求继续研究当前阶段，均保留待确认状态。收到修订意见时先更新本阶段结果。前提变化时回到最早受影响的阶段，下游结论标为待复核。
- 用阶段名称、结果版本、待确认事项、用户决定和下一步记录进度。恢复会话时按已记录的确认点继续。可继承用户已确认的范围，无须重复确认。用户明确只要求某阶段或指定核验任务时，交付该范围的结果，注明使用的输入与假设。

## 1. 判断品类

1. 用目标角色、典型任务、输入、期望输出和已知约束界定系统。给出一个主品类和判断依据，列出会扩大搜索范围的参考品类，说明每类可贡献什么。产品形态有歧义时并列说明哪些选择会改变候选池。
2. 用主品类和参考品类实际搜索开源项目，并盘点可复用的现有系统。按 [底座检索与核验手册](references/foundation-research.md) 查官方仓库、版本、许可、部署方式、入选理由和明显阻断，给出候选池。完成发现和初筛后，按手册给出初步匹配度百分比排名，默认详列前 10 名，其余列附表。逐个分点写明功能匹配、开源许可、二开风险、工程形态与集成、维护情况及与现有系统的关系。正式评分留在第 3 步。
3. 产品体验会影响品类或候选去留时，可安排子 Agent 查官方在线演示，或在用户已授权的环境和范围内试部署，打开真实页面，保留截图或可复现记录。实验的候选、环境、观察目标与交付字段见 [试部署与页面取证](references/foundation-research.md#2-试部署与页面取证)。

**请用户确认**主品类、项目业务边界和进入下一步的候选范围。暂时无法部署的候选可附证据局限继续初筛。

## 2. 拆解能力

1. 优先追踪一笔近期真实业务，从触发到完成，记录角色、操作、交接、异常、补救和结果。为可定位的原始材料编 E 号，区分观察事实、反馈、明确决定、推断与待验证事项。为卡点编 P 号并关联 E，记录频次、影响和测量口径。从这里起使用 `E1`、`P1`、`C1`、`R1`、`AC1` 这类无前导零的编号，后续沿用已登记的编号。缺数据时给出最小取证动作。
2. 按业务流程拆关键能力 C 和可验证需求 R。每条 R 关联 P、C 和 E，或追溯已确认约束。写角色、前置、动作、结果和验收条件，按需要补充权限、异常、迁移与审计。标注一期或后续、必需或可选、确认状态及业务验收状态。
3. 从 R 选出所有候选共用的计分项、必需项、硬约束和允许的交付方式。业务需求来自目标流程和证据。候选的 README、页面和功能可用于查漏，新增需求仍需业务依据。

**请用户确认**关键能力、一期范围、必需项和正式对照口径。将确认的清单作为第 3 步输入。

## 3. 对照底座

1. 用第 2 步确认的同一套用例对照候选，可按能力清单补搜遗漏项目。锁定版本、部署模式和观察时间，筛查许可、数据、部署与集成等硬约束。记录淘汰原因和仍待核实的约束。
2. 逐项查目标版本的 README、官方文档、源码、测试或运行记录，判断具备、部分具备、不具备、待核实。每项给出适用版本、证据、支持方式与差距。需用实测验证时，写明可复现条件，使用已有授权的隔离环境。页面观察、技术验证和正式业务验收分别记录。
3. 按 [报告模板](references/kickoff-report.md) 输出候选表及逐项证据。表前列品类、候选数和关键能力，表内并列匹配度与四态计数。先用硬约束和必需项判断推荐资格，再比较二开、迁移、运维、升级与退出成本。明确整套底座、可复用组件和组合方案的区别，组合覆盖需有集成证据。

**请用户确认**拟采用的底座或组合、改用既有工具或自建等实施路线，以及接受哪些缺口和验证前提。未知项保留为条件，需要时留在本步补证据。

## 4. 沉淀方案

1. 把前三步确认的业务边界、能力、所选路径和关键缺口落实到业务方案。按项目需要写功能需求、用户角色与权限、业务流程与状态、业务规则与异常、验收与开工条件。每项追溯到用户决定、需求或证据，同时保留未决事项、责任和验证动作。
2. 根据证据给出开工建议。核心流程和关键依赖有可行证据时建议「可开工」。关键适配问题可验证时建议「先试点」，附通过和停止条件。关键需求或前提缺证据时建议「先验证」，明确取证动作。收益有限或硬约束无可行解时建议「暂缓」，写明恢复条件。
3. 按 [报告模板](references/kickoff-report.md) 整理七节 PRD。涉及界面时，在第 4 节记录页面入口、操作、状态及 R/AC 对照，供后续制作原型。独立审查并补写后，运行 [PRD 校验脚本](scripts/check_prd.py)，核对候选分数、逐项矩阵和验证计划，再交付 Markdown。

**请用户确认**方案范围、验收与开工条件。确认前标为待确认稿。用户确认后更新到定稿。涉及界面且用户确认或明确要求用该版制作原型时，按 [原型评审规范](references/prototype-review.md) 另行制作和交付。

## 交付文件

文件名以可读项目名开头，使用用户指定的名称优先。将 Windows 文件名禁用字符换成连字符，保留中文项目名。`SKILL.md` 是技能加载入口的固定文件名。

| 交付范围 | 默认文件名 |
| --- | --- |
| 完整开工方案，包含同一份 PRD | `<项目名>-开工方案与PRD.md` |
| 单独的 PRD | `<项目名>-PRD.md` |
| 可交互原型 | `<项目名>-Web交互原型.html` 或 `<项目名>-移动端交互原型.html` |
| 需要交付视觉规范时 | `<项目名>-UI设计说明.md` |

完整开工流程仅交付一份 Markdown 需求文档。交互原型使用可离线打开的独立 HTML。有配套原型时放在同一目录，使用相对路径引用已实际生成的文件。

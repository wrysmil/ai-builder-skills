# 产品开工与原型评审

从用户要完成的任务出发，先还原人工业务，再判断品类和找候选。结合候选回访补齐流程，确认一期范围后对照底座，最后交付 PRD 和适用的交互原型。

## 按用户目标选择入口

默认走完整立项。用户明确限定任务范围时，使用相应的单项入口。

- **完整立项**：「帮我做个需求」「给我立项」「我要做个家教系统」等从第 0 阶段开始。用户已经确认的材料和决定直接继承。先说明准备调研的业务场景，完成预研再开聊。
- **直接写 PRD**：用户明确要求直接写、修订或续编 PRD 时，从第 4 阶段进入，按[七节 PRD 骨架](references/kickoff-report.md)与[填写规则](references/prd-structure.md)整理内部稿，并执行独立审查和 Markdown 交付。遇到影响范围或验收的缺口时按访谈规则定点澄清或标为待决。底座一节按实际记录已评估、未评估或明确排除。
- **只做 UI 或原型**：用户明确要求只做原型时，优先沿用已有 PRD。只有原始需求时，先从输入提取任务、页面和关键状态。按[交互原型评审规范](references/prototype-review.md)产出。
- **只找底座 / 只核验指定项目**：按给定范围交付，注明输入与证据局限。

## 阶段推进与文档记录

- 先找本项目已有的阶段记录并续写。没有记录时，在首次实质交付前按[阶段记录模板](templates/stage-record-template.md)创建 `<项目名>-开工阶段记录.md`。项目名未定时用当前能识别的业务短名，之后沿用同一份记录。优先放在项目已有文档目录，否则与项目交付物同目录。单项任务仅记录实际执行的阶段，也可沿用现有项目文档里的阶段记录区。
- 每轮有实质进展、用户决定、待确认、阻塞或回退时，更新「当前进度」、受影响的小节和需要留痕的决定。可写时先更新文档，再回复并附链接。只读时在回复内附更新后的 Markdown 记录。每个阶段保留输入及上游版本、证据、结果版本、状态、用户决定或待确认项、下一步。阶段记录用于续接，正式 PRD 沿用七节模板。
- 每轮推进当前阶段。需要用户决定时先展示结果及具体选择，收到明确确认或指示后再推进。单纯补充资料、跳过问题或静默均保留待确认状态。续接时比较项目文档与对话留档，按更新时间和版本采用最新可访问的记录，读其引用材料。只读回合留下的新记录在可写时并入同一份项目记录。若缺少必要记录，仅请用户补恢复点或决定所需的材料。
- 阶段 2 回访以及底座核验、PRD 审查或原型评审发现业务缺口时，按[后续发现与回退](references/business-discovery.md#后续发现与回退)记录。原有角色、业务边界或品类受到影响时回到最早受影响的确认点，把依赖原决定的结论标为待复核。已确认的评分口径发生变化时，确认新口径后用它重算受影响候选。

## 0. 业务发现与深度访谈

1. **首访前先完成业务预研。** 按[预研与首访指引](references/business-discovery.md)查用户已有材料，缺少流程依据时主动查行业操作手册、真实表单或从业者案例，也可看一两个产品的实际操作来理解流程，记为参考案例。自己先从触发到完成走一遍典型人工业务，掌握角色、输入、操作、判断、交接、结果及至少一个相关异常，并把流程草图、出处和待核实点写入阶段记录。资料不足以走通时，记录缺口，只请用户补一个能定位业务的实例或材料，继续补查后再进入访谈。
2. 带着流程草图和具体疑点开聊。先复述对相关业务的理解，请用户针对自己的做法纠正，再追一个真实案例。对用户特别关注的子流程，展开它的操作顺序、用到的材料、判断、产出与交接，有条件就对照一份实例。尚未运营的业务用有依据的类比走拟议案例，标清假设。关键分歧可提两三种做法与取舍。
3. **首访收尾时，先向用户总结系统上线后一笔典型业务大概怎么走。** 按[首访收尾总结](references/business-discovery.md#首访收尾总结)，用业务语言从触发讲到完成，说明谁接手、系统在哪些环节提供帮助、哪一步仍由人判断或线下完成，以及关键异常怎么处理。把总结写入阶段记录，标清已确认事项和待确认建议。继承已经明确的决定，请用户核对主流程、服务对象、关键角色和业务边界，再进入第 1 阶段。

## 1. 判断品类与候选初筛

1. **服务对象、关键角色与业务边界确认后，再正式检索开源底座。** 依据首访或用户已确认的材料给出主品类和依据，列出参考品类及各自用途。产品形态有歧义时，先确认会改变候选池的选择。首访前看过的产品，可按确认后的条件重新判断是否纳入候选。
2. 按[底座检索与核验手册](references/foundation-research.md)实际搜索开源项目并盘点已有系统。查官方仓库、版本、许可、部署方式和明显阻断。给出初步匹配度百分比排名，默认详列前 10 名，其余列附表。分点说明功能匹配、许可、二开风险、集成、维护情况以及与现有系统的关系。正式评分留在第 3 阶段。
3. 记录候选里值得回访的实际业务流程和证据。需要观察产品体验时，可安排子 Agent 查同版本官方演示，或在用户已授权的环境内试部署并保留可复现记录。见[试部署与页面取证](references/foundation-research.md#2-试部署与页面取证)。

**请用户确认**主品类、业务边界和纳入后续研究的候选范围。暂时无法部署的候选可附证据局限进入初筛。经检索未找到合格候选时，说明搜索范围和原因，请用户决定是否补搜或按空候选池继续。

## 2. 候选对照回访与拆解能力

1. 先把候选的页面、文档或已验证操作与人工流程逐段对照。按[候选对照回访指引](references/business-discovery.md#第-2-阶段拿候选流程回访)带着实际例子回访遗漏的角色、交接、异常和状态，也记录用户看了候选才想到的业务。能进行对照但无实质新增时，留档依据并继续。没有可用的候选流程证据时，按指引用业务材料复盘，注明候选对照受限。
2. 把回访确认的业务事实或决定写回第 0 节流程和证据。候选功能附技术来源，进入一期须有业务依据和用户确认。为原始材料编 E 号，卡点编 P 号并关联 E，记录频次、影响及仍需测量的指标。为关键能力编 C 号，需求编 R 号，验收编 AC 号。使用 `E1`、`P1`、`C1`、`R1`、`AC1` 这类无前导零编号，后续沿用。
3. 每条 R 追溯到 P/C/E 或已确认约束，写清角色、前置、动作、结果和可测验收。按需补充权限、异常、迁移与审计。标注优先级、是否一期、确认状态和业务验收状态。从 R 选出所有候选共用的计分项、必需项、硬约束及允许的交付方式。

**请用户确认**回访中仍影响范围的决定、一期范围、必需项和正式对照口径。以确认的版本作为第 3 阶段输入。

## 3. 对照底座

1. 用第 2 阶段确认的同一套用例对照候选，可按能力清单补搜遗漏项目。锁定版本、部署模式和观察时间，筛查许可、数据、部署与集成等硬约束。记录淘汰原因和待核实条件。候选池已确认且仍为空时，记录零个可核验底座与搜索边界，按相同业务目标和硬约束比较可用路径，候选匹配度标为不适用。
2. 逐项查目标版本的 README、官方文档、源码、测试或运行记录，判断具备、部分具备、不具备、待核实。每项给出适用版本、证据、支持方式和差距。需实测时使用已授权的隔离环境，分别记录页面观察、技术验证和业务验收。
3. 按[报告模板](references/kickoff-report.md)输出候选表及逐项证据。表前列品类、候选数和关键能力，表内并列匹配度及四态计数。先按硬约束与必需项判断推荐资格，再比较二开、迁移、运维、升级与退出成本。明确整套底座、可复用组件与组合方案，组合覆盖需有集成证据。

**请用户确认**实施路线、保留的缺口和验证前提。未知项保留为条件，需要时留在本阶段补证据。

## 4. 沉淀方案与 PRD

1. 用阶段记录中已确认的业务流程、一期范围、实施路线和缺口写七节内部稿。直接写 PRD 时用现有材料和已确认的决定，记录跳过的阶段并保留影响范围或验收的待决项。覆盖角色与权限、流程与状态、规则与异常、验收及开工条件。涉及界面时记录页面入口、操作、状态和 R/AC 对照。
2. 根据证据给出「可开工」「先试点」「先验证」或「暂缓」。验证或试点写清执行人、输入、阈值、产出证据与停止条件。技术验证须按用户授权开展。
3. **每次向用户交付 PRD 前，包括首稿、修订稿和定稿，必须完成[独立 PRD 审查](references/prd-review.md)。** 把原始材料、阶段记录和内部稿交给子 Agent 查漏并拟写补充，返回后核对、补写，再运行[PRD 校验](scripts/check_prd.py)并核对候选分数及验证计划。仅格式或状态变化时让子 Agent 对照已审查版本核对差异。无法派遣或尚未取得有效审查时保留内部稿、记录阻塞，等待审查后交付。
4. **先单独交付已审查的 Markdown PRD**，写明实际补入的需求、验收和待决事项。请用户确认范围、验收与开工条件。确认前标为待确认稿，确认后更新为定稿并留档。无界面项目在 PRD 记录相应评审材料和确认条件。

## 原型与评审

涉及界面的完整立项，先交 PRD，收到用户确认或明确要求基于已交付版本制作后，再按[原型评审规范](references/prototype-review.md)制作并另行交付原型。记录输入 PRD 版本、覆盖范围、验证与用户反馈。涉及界面时在原型评审后讨论开发与排期。只要求 PRD 时到文档交付为止。

## 交付文件

文件名优先使用用户指定名称。使用中文项目名时将 Windows 禁用字符换成连字符。有配套文件时使用相对路径引用已经生成的文件。

| 文件用途 | 默认文件名 |
| --- | --- |
| 过程记录 | `<项目名>-开工阶段记录.md` |
| 正式开工方案与 PRD | `<项目名>-开工方案与PRD.md` |
| 单独 PRD | `<项目名>-PRD.md` |
| 可离线打开的交互原型 | `<项目名>-Web交互原型.html` 或 `<项目名>-移动端交互原型.html` |
| 需要交付的视觉规范 | `<项目名>-UI设计说明.md` |

# PRD 条款写法

## 需求条目的句式

**主体 + 行为 + 结果。**

```
系统 + 应/须 + 可观察的行为
```

- ✅ `系统在保存网点服务商配置前应校验同一网点是否已配置同一服务商。`
- ✅ `网点服务商配置列表应支持按网点、服务商、配置状态三个条件筛选。`
- ❌ `网点配置功能`（没有行为，不是需求）
- ❌ `系统应该能方便地配置网点`（"方便"不可观察，不可验收）
- ❌ `支持网点配置和订单转自提判断`（两件事挤一条，无法编号、无法验收）

## EARS 句式（验收标准的写法）

每条 AC 只判一个是非，用下列句式之一：

| 句式 | 用途 | 例 |
| --- | --- | --- |
| 当〈触发条件〉时，系统应〈结果〉 | 有明确触发 | 当输入的网点编码不存在时，系统应提示"网点不存在" |
| 若〈条件〉，则系统应〈结果〉 | 条件分支 | 若同一网点已配置同一服务商，则系统应拒绝保存 |
| 在〈状态/期间〉期间，系统应〈结果〉 | 持续状态 | 在配置状态为"启用"期间，系统应在列表中显示该配置 |
| 在〈条件〉下，系统应〈结果〉 | 约束前提 | 在用户无网点数据权限时，系统应隐藏网点筛选条件 |
| 系统应〈结果〉 | 无条件基线 | 系统应记录每次配置变更的操作人与时间 |

**一条 AC 一个判定。** "拒绝保存并提示错误"其实是两个判定，拆成 AC1（拒绝保存）、AC2（提示内容）。

## 字段写法

需求里提到具体字段时，写全这 11 项（不适用写"不适用"，不要留空）：

字段名 · 含义 · 控件类型 · 是否必填 · 默认值 · 取值来源 · 格式/长度 · 唯一性 · 是否可编辑 · 错误提示 · 所属页面

**字段名三处一致**：PRD、后续原型、代码/接口文档必须同名。改字段名要同步改编号对应的需求条目，不能只改一处。

## 按钮与状态命名

- 按钮名用动词短语，写清点了会发生什么：`保存配置`（不是"提交"）、`启用配置`（不是"确认"）。
- 一个动作在全文只用一个名字：按钮叫"保存配置"，成功提示就是"配置保存成功"，不换成"提交成功"。
- 状态名用名词/形容词短语，全文统一：`启用` / `停用` / `待审核` / `草稿`。不要一会儿"已启用"一会儿"启用中"一会儿"正常"。

## 错误与提示写法

错误提示要说清**哪里错 + 怎么改**：

- ❌ `操作失败`
- ✅ `该网点已配置服务商「顺丰」，请更换网点或先删除原配置`

提示文案属于可替换层，写进 PRD 没问题，但**判定条件必须写清**（什么情况下出现这条提示）。

## 常见反模式

| 反模式 | 为什么坏 | 怎么改 |
| --- | --- | --- |
| 把技术方案当需求 | "用 Redis 缓存配置" 是实现，不是需求 | 写"配置查询响应 ≤ 2s" |
| 把假设当已确认 | 研发按编的规则实现，一周后返工 | 分三类标注，假设单列 |
| 一条需求写多件事 | 无法编号、无法验收、无法估工时 | 拆成多条，各自编号 |
| 无验收标准 | "做完了"没有客观标准 | 每条需求至少一条 AC |
| 验收标准不可测 | "界面要美观""响应要快" | 用 EARS 句式写出可观察的行为和具体阈值 |
| 需求扩散 | 用户没提的批量导入、审批流全加进来 | 移到"不在本期范围" |
| 遗漏异常路径 | 只写成功流程，研发不知道失败怎么办 | 每条写操作都要有失败分支 |
| 界面即需求 | "做一个红色按钮" | 写用户要达成什么，界面是原型的活 |
| 编号重排 | 历史 PR、测试用例、缺陷单的引用全断 | 续编不重排，作废留号 |
| 覆盖矩阵有洞 | 某条需求没人验收，测试也漏了 | 跑 `check_prd.py`，一个 ❌ 都不能留 |

## 自检清单

写完逐条过：

- [ ] 每条需求编号稳定且无重复
- [ ] 每条需求一句话，只表达一个行为
- [ ] 每条已确认的一期需求有 AC，待补条目显式标记
- [ ] 每条 AC 引用的需求都存在（无悬空）
- [ ] 每条 AC 用 EARS 句式，且只判一个是非
- [ ] 每条 AC 都能被测试同学写成一条测试用例
- [ ] 已确认 / 合理假设 / 待确认三类分开，假设和待确认各自单列
- [ ] 每个待确认项都写了"不确认会卡住什么"
- [ ] 字段表 11 项齐全，不适用项写明"不适用"
- [ ] 字段名/按钮名/状态名全文一致
- [ ] 每条写操作都有失败分支和用户反馈
- [ ] 范围一节明确写了"不在本期范围"
- [ ] 非功能需求给了具体阈值，不是"要快"
- [ ] 版本记录已建
- [ ] `python scripts/check_prd.py <文件>` 通过

## 交付话术

交付时给用户这几样，不要只丢一个文件路径：

1. 文件路径 + 需求条数（R）
2. AC 条数 + 覆盖矩阵有没有缺口
3. **待确认事项几条**，列出最关键的 2-3 条（需要用户拍板的）
4. 做了哪些合理假设（列出来让用户能否掉）
5. 下一步建议：按本技能生成交互原型或直接排期

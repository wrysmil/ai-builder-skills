# 在开工方案中写 PRD

用 [PRD 模板](../templates/kickoff-prd-template.md) 起稿。保留七节的二级标题和顺序，将版本、评审状态和修订说明写在正文或版本记录中。

在首次登记和后续每次引用时，使用字母前缀加无前导零的正整数，例如 `E1`、`P1`、`C1`、`R1`、`AC1`。各类编号独立续编，原编号可保留空缺。已有外部 PRD 仅用于制作原型时，继续引用它的原编号。

- 第 1、2 节写决策、目标、范围、角色、入口、限制和现有流程。
- 第 3 节用「编号｜证据｜来源与局限」登记 E，用「编号｜痛点｜关联证据」登记 P。用户确认的约束也可登记为 E，来源写明用户决定。无痛点证据时标待取证，R 可先引用明确约束；草稿暂时无来源的 R 在状态写「待确认」。
- 第 4 节保留 C（能力）和 R（需求），增加 AC（验收）。功能、规则、权限及可验证的非功能要求共用 R 编号。每条 R 写一个可检验的行为，注明角色、入口或前置条件、结果、优先级和状态。需求的「来源」可列 E、P、C；通过 P 或 C 能追溯到 E 时也算有证据。标为「已确认」的需求应能追溯到 E。新增条款续编，已用编号保留，退出一期的条款可在状态标「已作废」或「已移出一期」。
- AC 写可观察的触发条件、结果和证明方式。覆盖矩阵从 R 到 AC、也能从 AC 追溯 R。需要原型时增加页面与区域列，原型右栏沿用对应 R/AC。未确认需求如果暂缺 AC，矩阵标「待补」；已确认需求必须有 AC。设计和技术验证与业务验收状态分别记录。
- 第 4 节可增加页面、字段、状态、权限、异常、迁移和数据埋点明细。标注适用范围及对应 R。字段记录类型、来源、必填、默认值、取值和错误反馈。验收句式见[条款写法](writing-rules.md)。
- 第 5 节保留候选底座与各自技术证据，候选覆盖与产品 AC 覆盖分别成表。只写 PRD 且无底座评估时，在此注明。
- 第 6 节写验证目标、方法、通过或停止条件。第 7 节分别记录合理假设、待确认事项、开工条件和版本变更。未经确认的条件标注对范围或验收的影响。

交付前按[独立 PRD 审查](prd-review.md)派遣子 Agent 查漏，复核并将补项写回文档，再运行 `python scripts/check_prd.py <PRD路径>`。可加 `--json`。脚本覆盖七节结构、来源编号、需求与验收双向覆盖，业务覆盖由独立审查核对。

# 开源底座检索与核验手册

第 1 步使用第 1、2 节，以初步业务边界、品类、已知约束和假设发现候选。第 3 步使用第 3–6 节，根据用户确认的 R 清单和对照口径完成正式评估。用户只要求核验指定候选时，按所给范围说明输入和证据限制。

## 1. 选工具并执行检索

| 工作 | 优先使用的工具 | 受限时的替代路径 |
| --- | --- | --- |
| 查已有实现 | 项目文档、依赖清单、配置、代码搜索、现有流程记录 | 盘点用户提供的系统材料，标记仓库和部署信息缺口 |
| 发现开源候选 | GitHub 仓库搜索，优先用 GitHub 连接器，其次平台搜索、`gh search repos` 或 GitHub Search API | GitLab、Codeberg 等适合该生态的托管平台，或 Web 搜索限定官方组织和托管域名 |
| 扩大候选面 | 通用 Web 搜索，DSH 可用免费搜索的 `web_search` 或 `advanced_search`，结果偏窄时用 `multi_search` | 换检索词、语言或来源类型，查技术生态目录、包注册表、已有平台的官方集成目录 |
| 取一手证据 | `web_fetch` 或浏览器读取官网、版本文档、发布说明，仓库连接器或 API 读取指定 tag / commit 的源码、测试、部署和许可文件 | 只读获取仓库，按目标版本检索文件、接口、测试和配置。带上可定位的链接或路径 |
| 查发布与维护 | 官方 Releases、Changelog、支持政策、包或镜像注册表、归档状态和公开维护记录 | 核对源码标签、制品和最近维护证据，无法确认的字段保留未知 |
| 核验许可和已知风险 | 目标版本组件和插件的许可证、商业条款、SPDX，项目公告及适用的 OSV、GHSA 等数据库 | 记录涉及的组件和版本、部署或分发模式以及证据缺口，无法核对时保留待核实 |

1. 先查当前系统能否配置、扩展或复用。外部搜索用业务任务分别组词，包括 `品类 + 部署条件`、`核心动作 + 输入输出或业务规则`、`同义词或相邻品类 + 关键集成`。已知项目可用作搜索替代品的入口，最终仍按 R 判断。GitHub 可用 `in:readme`、`topic:`、`archived:false` 等限定词缩小范围。会漏掉可用候选的条件留到第二轮过滤。

   如果允许商业平台或托管服务，同时搜厂商和集成目录。用官方套餐、区域、API、支持与导出条款核验，记录当期套餐和取证日期。用户限定开源时按开源源码、许可和目标部署筛选。
2. 对未指定候选的实质性选型，默认覆盖代码托管搜索和通用 Web 搜索。两路明显重复或命中不足时，补充另一类来源或检索表达，说明覆盖边界。多个引擎转引同一材料算同一来源。为每轮保存日期、实际查询、渠道、命中或限制、由此新增或淘汰的候选。
3. 把每个命中落到官方项目标识、规范仓库 URL 或可验证的源码发布入口。区分原仓、独立维护的分叉、镜像、云服务、开源版和商业版。确认是否存在、可读、归档、迁移或仅提供源代码查看。未经核实的提名留在检索记录里。对 403、限流、网络错误、404 分开记录，尝试官方镜像、版本文档或发布记录，保留原因和不确定性。
4. 做一轮硬约束初筛。每个初选候选带规范仓库或官方入口、入选理由、可能阻断和已有证据。标出整套系统、组件或商业对照。已有可信候选且补搜不再改变范围时停止。找不到合格候选时保留搜索边界、主要淘汰原因及可行路径。尚未落到规范入口的提名只留在检索记录。按下列口径输出第 1 步候选池。

### 初步匹配度与推荐理由

先按已知业务边界、部署及对外计划筛查推荐资格。若确认许可、部署或数据等硬约束冲突，列入仅供参考或淘汰附表。关键约束待核实时标为条件候选，写明核实事项。许可按目标版本和实际使用、修改、网络提供服务及分发方式核对。非商业条款与计划商用冲突时排除，无明确许可时先核实所需权利。AGPL 按实际部署方式及可接受的义务判断。高功能分不能抵消硬约束冲突。

| 初筛维度 | 默认权重 | 看什么 |
| --- | ---: | --- |
| 核心功能匹配 | 40 | 主任务、关键动作、输入输出和异常处理 |
| 开源与许可 | 15 | 核心代码是否开放，关键能力是否依赖闭源或付费服务，许可是否适用 |
| 二开风险 | 15 | 需改动的范围、技术限制、升级合并与长期维护负担 |
| 工程形态与集成 | 15 | 库、CLI、API 或整套系统的接入方式、部署和运行条件 |
| 维护情况 | 5 | 发布记录、近期修复、支持窗口及归档状态 |
| 本地化与目标环境适配 | 5 | 项目所需语言、数据格式和运行环境 |
| 复用价值与系统重叠 | 5 | 能填补的现有缺口、可复用范围及重复建设程度 |

所有候选用同一套维度和分母。可按当前领域调整权重，统一调整到 100，并在表前公开维度、权重、关键假设和证据范围。每项按证据打 1（充分匹配）、0.5（部分匹配）或 0（无匹配证据）。0 分须区分已有证据表明不匹配和待核实。**初步匹配度 = 各项权重 × 对应得分的总和 ÷ 总权重 × 100%**。给出各项得分或简明分项算式以便复算。按未取整分数降序，同分先列核心功能分较高者，再看待核实项较少者。第 3 步再按确认后的 R 用例计算正式匹配度。

先列默认前 10 个可推荐候选，候选不足时按实际数量列出，用户指定数量时以用户要求为准。其余候选用附表给出分数和处置，条件候选标明条件，商业对照及淘汰项标明用途或原因。前排候选逐个分点说明以下内容，并附规范入口和对应证据。缺证据标待核实。

- **功能匹配**逐项写出对应业务动作和产物，指向具体功能、命令、接口或实测结果，标明部分覆盖的边界。
- **开源与许可**写明许可和源码覆盖范围，区分开源核心、外部闭源或付费能力及关键依赖条款。
- **二开风险**写明具体缺口、需改动的范围和已知限制。未知成本保留待核实。
- **工程形态与集成**写明整套底座、组件或参考实现，可用入口、部署条件和接入方式。
- **维护情况**引用发布、修复或支持证据，星标和开放 issue 数仅作信号。
- **与现有系统的关系**写明可复用什么、补足什么以及哪里会重复建设。没有既有系统信息时注明待核实或不适用。

## 2. 试部署与页面取证

- 优先选能澄清品类或去留的候选，先找同版本的官方演示。在线演示省去部署，须注明版本和部署差异。无可用演示，且用户已授权试部署时，可把独立候选交给子 Agent 在隔离环境实跑。无子 Agent 时可由主 Agent 执行；缺环境或权限时记录阻塞，用官方说明和截图补充并标明来源。
- 主 Agent 给出规范仓库、目标 tag／commit 或镜像、用户已授权的环境和操作范围、观察路径、预算与停止条件。子 Agent 先核对官方部署说明和配置，再使用独立目录与端口及合成样例。使用现有授权范围内的资源。观察可从启动、本地访问延伸到导入、编辑、预览、导出等与品类有关的可达页面。候选只有 CLI 或 API 时，观察可运行入口或接口响应。
- 回传版本、环境、操作步骤、访问地址、页面截图或运行记录、实际看到的流程、失败原因及环境状态。需供用户查看的实例注明访问方式与保留期限，临时资源按约定收尾。主 Agent 复核版本与结论，把证据限定在已观察的页面和流程。可见按钮仅能证明页面入口，行为须实际运行或查实现。

## 3. 锁定版本并核查硬约束

- 将仓库、发布制品、目标 tag 或 commit、部署模式、版本类型及核验日期记在一起。用户未指定时，选与环境相符且证据可核对的发布版本，说明选择原因。默认分支上的实现仅支撑对应提交。最新版文档、路线图、未合并 PR 或另一版本的行为不能证明目标版本具备能力。
- 按已确认硬约束分别查许可、部署拓扑、外部服务和网络需求、数据驻留、鉴权、资源预算及关键集成。功能在付费版或外部服务中才可用时，明确适用版本、前提和相应约束结果。社区插件需核对源头、版本兼容和持续维护责任。
- 许可证按实际使用、修改、网络提供服务和分发方式核对。定位目标版本 `LICENSE`、实际使用的组件或插件条款及适用范围。有关键条款歧义时记录要核对的决定，保持待核实。仅能查看源码或许可证缺失的项目按可确认的权利范围处理。
- 维护至少核对与决策相关的发布、近期修复、支持窗口或归档状态。记录日期和来源。星标、下载量和最近提交只作信号。安全及合规结论注明已查版本、数据源和范围。

## 4. 建立逐项覆盖矩阵

将各候选映射到同一套 R 和验收用例。每格记录 `R / 用例 → 状态 → 版本化证据 → 可用方式 → 剩余差距 / 验证动作`。打开源材料后保留短摘录、章节锚点或精确文件路径。对于代码证据，指出规则实际执行或被测试的位置。

| 状态 | 判定 |
| --- | --- |
| 具备 | 有适用版本的一手证据支持这个用例的全部被评估条件，且可用方式在本轮允许范围内。若依赖配置或允许的插件，明确版本和前提 |
| 部分具备 | 有证据支撑其中一部分，同时记录其余条件的已知缺口或未知项。需二开才能补齐时写明补齐范围 |
| 不具备 | 有版本化的限制、代码或试验证据表明用例无法在本轮允许的交付方式内完成 |
| 待核实 | 现有材料不足以判断任何实质性覆盖，或来源冲突仍无法按目标版本和环境解决 |

README 或官方文档能证明的范围，以其实际描述为准。功能名称或概括性的宣传语不足以证明某条验收条件。规则、接口、隔离、迁移、性能等约束超出描述时，补查版本化源码、契约、测试或隔离环境运行结果。有限的字段和用例测试只说明当时覆盖的范围。要确认能力缺失，需定位明确的版本限制、实际实现边界或符合验收前提的失败结果。

研究中遇到冲突，先比对版本、版本类型、部署、插件和测试前提，再核对更具体的证据。解释为什么当前结论仍可能变化。对于可能阻断决定的判断，尽量用交付说明与实现／测试等不同证据交叉核验，只有单一可靠来源时写明局限。

有必要且有权限时，在隔离环境用合成或脱敏数据做最小试验。先定义要查的 R 或硬约束、版本及环境、正反用例、输入、期望与停止条件，再记录实际结果及覆盖范围。试点方案要检查适用的硬约束，复验会受目标环境影响的条件，并跑通核心流程；前期证据和正式验收分别记录。仅完成只读研究时，交付试验计划。研究、安装运行、上传材料和生产验证分别按用户授权执行。公开查询使用去敏后的品类和需求词。

## 5. 选择单 Agent 或多 Agent

- 单候选、低风险且文档和代码足以核验时，由一个 Agent 完成逐格核查。多源检索和证据交叉检查可以由同一个 Agent 执行。
- 候选多、涉及多条业务或生态方向、证据明显矛盾，或许可、数据迁移、权限等疑问会改变决策时，优先分派独立子任务。主 Agent 先发同一版 R 清单、硬约束、允许方式、时间和输出字段。可分派候选发现、按候选分组的逐项核验，以及独立复核可能阻断排序的结论。涉及内部材料时按任务使用必要的脱敏摘要。
- 各 Agent 回传检索渠道与查询、规范仓库、版本或模式、对应 R、证据定位、状态与局限。主 Agent 去重、抽查关键结论、处理分歧，汇总为一个矩阵。发生冲突时回到同一版本的一手证据，仍不确定就保留待核实。多位 Agent 引用同一页只贡献一份证据。
- 无子代理能力时，单 Agent 分轮执行发现、核验和反向复核。反向复核专查排名靠前候选的必需项、硬约束和反证，记录实际完成的工作。

## 6. 形成可解释的建议

1. 先汇总已确认的硬约束冲突和待核实项，再看必需用例覆盖。分别说明候选可详评、可有条件试点或应淘汰的依据。涉及关键未知时，只给条件性顺序。
2. 按相同业务目标比较可行路径。列出配置、插件、适配层、二开或自建各自需要承担的集成、迁移、数据导出、运维、升级合并、维护责任和退出工作。缺实测时用定性范围或注明假设。
3. 先列本轮考虑的底座品类、实际纳入的候选数、对照的关键能力及对应 R 或子用例。候选表在项目名称旁并列「匹配度」和「四态计数」，按 [报告模板](kickoff-report.md) 统一计算和排序。每个数字都从同一套逐项矩阵汇总，注明已知缺口与关键未知。硬约束和必需项决定推荐资格。不同层级的候选采用同一全局口径，并注明组件用途。
4. 回写每个重要缺口影响的 R、验证动作和开工前提。给出首选、条件性备选或其他可行路径，写清什么证据会调整推荐。验证顺序优先处理能最快排除不可行方案的事项。

# 独立 PRD 审查

## 派遣与输入

内部稿写完、对用户交付前，用子 Agent 工具派至少一位独立审查者。提供内部稿路径或全文、原始需求与附件位置、阶段记录中相关的人工流程、首访和回访答复、用户确认与修订记录、一期边界和明确排除项。让审查者先从原始材料还原应覆盖的需求，再与 PRD 对照。原型、候选底座、行业参考和草稿可用于查漏，业务承诺以可追溯的业务依据和确认记录为准。材料有缺口时，记录未覆盖的来源与影响。

## 查漏维度

| 维度 | 核查问题 |
| --- | --- |
| CRUD 与对象生命周期 | 逐个核心对象检查谁能新增、查询、查看、修改、删除或停用。看状态限制、关联对象、已有数据和例外。仅对适用的操作追问或补写，明确不适用或已排除的原因。 |
| 交互逻辑 | 按角色从入口走完主流程和返回路径。检查默认值、校验、成功、空态、失败恢复、取消与重复提交。对正文或页面表已经承诺的反馈和状态，检查是否有对应验收。 |
| 业务覆盖 | 逐条对照原始要求和最新确认，查角色、业务目标、触发条件、交接、状态转换、例外、人工兜底及范围边界。找出留在正文、会议纪要或附件、还未落到需求和验收的约束。 |
| 权限与数据 | 结合项目检查角色和数据范围、替代入口、字段可见性、唯一性、导入导出、历史数据与数据一致性。必要时覆盖失败后或重试后的实际数据结果。 |
| 运行条件与验收 | 检查项目明确要求的部署、外部依赖、性能与可靠性。核对验收前提、输入、预期和证明方式，业务验收与技术验证分别记载。 |

## 回传与补写

要求审查者对各维度回传发现或简述已检查的样本。每条发现写明来源与定位、现有 R/AC 或缺失位置、具体影响，以及建议补写的 R、AC 或待确认问题。确认为遗漏的条款附上可直接合入的文字。结果区分已有依据的遗漏、需要业务决策的疑问和已排除事项。交叉核对原始输入，避免把推断变成承诺。

主 Agent 逐项复核并落实处理。把有依据的遗漏补进 PRD 正文、验收用例和双向覆盖矩阵，保持原编号并为新条款续编。把无依据或相互冲突的业务选择写进第 7 节，给出影响和待决定的问题。若发现可能改变已确认的角色职责、业务边界、一期范围或底座选择，按[后续发现与回退](business-discovery.md#后续发现与回退)回到相应的确认点，暂缓交付受影响的版本。用户确认处理方式后，更新受影响的权限、需求、验收和底座结论，并把改过的业务条款交给子 Agent 复核。单独写 PRD 时在当前任务范围内定点澄清，未确认事项按实际影响写入待决。随后检查补写后的正文和矩阵并运行 `python scripts/check_prd.py <PRD路径>`。在第 7 节记下审查版本、主要补项对应的 R/AC、剩余待确认项，并在交付消息中突出这些改动。结构校验通过只能证明编号及关联符合约定。
